# Architecture Journey Retrospective — 2026-05-17 to 2026-08-17

## Purpose

This document consolidates architecture-related discussions from the three-month period ending 2026-08-17. It is intentionally a learning/decision log rather than a production specification.

Labels used below:

- **【Fact】** directly provided by the exercise, repository history, or current project context.
- **【Decision】** a design choice made during discussion.
- **【Inference】** an architectural conclusion derived from assumptions and constraints.
- **【Open】** unresolved or requiring current documentation / benchmark validation.

## 1. Global URL Shortener

Existing case study: `case-studies/01-url-shortener/README.md`

### Problem and scale discussed

- **【Fact】** 100M new URLs/day.
- **【Fact】** 10B redirects/day.
- **【Fact】** redirect P99 target < 50 ms.
- **【Fact】** 99.99% availability.
- **【Fact】** retention at least 5 years.
- **【Inference】** average create rate ≈ 1,157 writes/s and redirect rate ≈ 115,741 reads/s.
- **【Design assumption】** a 10× peak factor was used for capacity reasoning until real traffic traces are available.

### Key design decisions preserved from discussion

- `POST /v1/urls`, `GET /{shortCode}`, and stats API were separated by workload characteristics.
- Short-code uniqueness belongs in an authoritative write boundary; retry safety requires an idempotency key.
- Redirect is the latency-critical path; click analytics must be asynchronous so analytics failure cannot block redirect.
- Cache hierarchy should be sized by active working set, not total five-year data size.
- Metadata mapping is preferably immutable, while lifecycle status can change (`active`, `disabled`, `expired`).
- Redirect metadata may tolerate a weaker read model than unique creation, but the acceptable global-visibility delay needs an explicit SLA.
- Local cache versus managed Redis and cache eviction/negative caching were discussed as trade-offs, not universal defaults.

### Open validation items

- Global visibility SLA after creation.
- Cache hit ratio and working-set size under production-like traces.
- Metadata item size and replicated storage cost.
- Analytics freshness and retention.
- Exact consistency mode and failover behavior for the selected database.

## 2. Global Rate Limiter

Existing case study: `case-studies/02-global-rate-limiter/README.md`

### Core discussion

The design explored how to enforce a global user quota without making every request synchronously depend on one globally consistent counter.

### Key decisions

- **【Decision】** User quota state is partitioned by `userId` in a NoSQL-style authoritative store.
- **【Decision】** Regional Redis/cache holds leased/session quota so the hot path can decide locally.
- **【Decision】** Each region receives quota based on recent usage, with a discussed upper-bound pattern similar to `min(previous-minute-usage × 2, global quota)`.
- **【Decision】** Multiple local sessions may borrow quota within the duration, but the total lease cannot exceed the user's global allowance.
- **【Decision】** The rate limiter decides admission; backend usage records are authoritative for actual billing/consumption reconciliation.
- **【Decision】** Requests carry a requested timestamp, while backend timestamps/idempotency identifiers are used for reconciliation and deduplication.
- **【Decision】** Missing records are repaired/reconciled rather than rolling back already-served requests.

### Failure semantics discussed

- Free tier can fail closed when global coordination is unavailable.
- Enterprise traffic can fail open only within already leased local quota / TTL boundaries.
- Local persistence and lease expiry are used to avoid a reconnect storm after control-plane recovery.

### Core trade-off

The system intentionally accepts bounded temporary overshoot in exchange for low-latency regional admission and resilience to inter-region failure. The important architectural question is therefore not “can overshoot be eliminated?” but “what overshoot bound is contractually acceptable and how is it reconciled?”

### Open validation items

- Exact lease duration and replenishment interval.
- Maximum permitted overshoot by customer tier.
- Recovery behavior after long partitions.
- Hot-key behavior for extremely large tenants.

## 3. Notification System

Existing case study: `case-studies/03-notification-system/README.md`

### Event-driven design discussed

- Kafka/event streaming is used to decouple producer traffic from provider delivery.
- Worker parallelism scales through partitions/consumer groups.
- A first-stage worker resolves subscription/user targets; downstream work is fanned out to another topic for actual delivery.
- Cross-region replication/mirroring was considered for regional resilience.

### Reliability decisions

- **【Decision】** Treat provider delivery as at-least-once and make delivery processing idempotent instead of assuming exactly-once end to end.
- **【Decision】** Persist processing milestones so retries can determine which step already completed.
- **【Decision】** Use explicit idempotency keys / notification identities for deduplication.
- **【Decision】** Provider rate limits belong behind a controlled sending layer rather than being ignored by Kafka throughput planning.
- Retry, timeout, rollback boundaries, and a terminal/done path were discussed as separate concerns.

### Strong consistency discussion

A later discussion challenged the idea that avoiding duplicate notifications automatically implies using a strongly consistent database.

- **【Inference】** Strong database consistency can protect state transitions, but it does not by itself produce exactly-once delivery across a database + queue + external provider boundary.
- **【Decision direction】** The more useful primitives are an idempotent notification identity, transactional state transition/outbox-style boundary where needed, provider response recording, and reconciliation.
- **【Open】** Cosmos DB Strong versus SQL should be chosen based on data model, transaction boundary, access pattern, multi-region requirements, and cost—not simply because duplicate notifications are undesirable.

## 4. Global Load Balancing on Azure

Existing case study: `case-studies/10-global-load-balancer/README.md`

### Questions explored

- Traffic Manager capacity and DNS-level limitations.
- Whether Traffic Manager can meaningfully front Azure Front Door endpoints and what addressing/routing semantics apply.
- Front Door profile/resource limits and whether multiple independent Front Door deployments are required at very high request rates.
- Why a multi-service architecture can provide a higher composite availability target than relying on a single component.

### Architecture lesson

Global routing, edge reverse proxying, regional load balancing, and application scaling are distinct layers. “Use more load balancers” is not sufficient: each layer must have a failure domain, health signal, routing policy, and capacity model.

### Open validation

## 5. Azure Hosted Agent with Session Memory and RAG

### Requirement discussed

The desired agent needs:

- a `sessionId` / conversation identity so a later request can continue prior context;
- RAG over an external knowledge source;
- a hosted execution model on Azure AI Foundry;
- the option to reason about whether a conversation can finish in one request and when server-side session state is still useful.

### Component model

The discussion decomposed the architecture into:

1. agent/runtime endpoint;
2. conversation/session state;
3. retrieval tool / knowledge index;
4. model deployment and tool orchestration;
5. durable business state kept outside transient model context where necessary.

### Key architectural distinctions

- **【Inference】** “Session memory” and “RAG” solve different problems: session memory preserves conversational continuity, while RAG retrieves external knowledge.
- **【Inference】** A single request can complete a task if all required context and tool calls fit the execution, but a stable session identity is still useful for multi-turn continuity and audit/replay.
- **【Decision direction】** Business-critical state should not rely only on opaque chat history; persist explicit application state when correctness depends on it.
- **【Open】** Exact Hosted Agent session/thread APIs, retention, tool invocation semantics, and offline constraints must be validated against the current Azure AI Foundry API version.

## 6. APIM AI Gateway and Azure AI Foundry Priority Processing

### Question discussed

Could APIM AI Gateway load-balance traffic across two model deployments to get around a Priority Processing rule described as allowing no more than a +50 increment within 15 minutes? How can we determine whether the Priority Processing behavior is enforced per deployment or at a broader scope?

### Architecture reasoning

- APIM can be used as an AI gateway for routing, policy enforcement, observability, and load balancing across backends.
- Whether multiple deployments increase an effective Priority Processing allowance depends entirely on the enforcement scope of the underlying quota/ramp rule.
- **【Important】** The gateway cannot legitimately “remove” a platform quota; it can only distribute traffic across independent quota domains if the service actually defines them as independent.

### Proposed verification pattern

1. Create two otherwise equivalent deployments.
2. Establish the same baseline load for each.
3. Increase deployment A toward the suspected ramp threshold while keeping B unchanged.
4. Observe whether throttling/priority behavior on A affects B.
5. Repeat with the traffic split through APIM to separate gateway behavior from model-service enforcement.
6. Capture response status, headers, deployment identifier, timestamps, token/request rates, and Azure metrics.

### Open

The quota scope and the exact “15-minute/+50” rule are service-version-dependent and should be recorded as **unverified until confirmed by current Microsoft documentation or controlled experiment**.

## 7. Azure SQL for MVP Architecture

### Question discussed

Which Azure managed relational database option is appropriate for an MVP, with emphasis on SaaS/PaaS simplicity rather than self-managed infrastructure?

### Architecture lesson

For MVP selection, the useful decision dimensions are not only feature completeness but also:

- operational overhead;
- compatibility with the application framework;
- expected scale and connection pattern;
- serverless/auto-pause characteristics where available;
- migration path if the MVP grows;
- cost predictability.

## 8. AI Agent Flow / Offline Feasibility

A customer-style agent flow diagram was reviewed to identify the responsibilities of each component and ask whether the flow could operate offline.

### Durable lessons

- “Offline” must be decomposed into model inference, retrieval/index access, orchestration, identity/authentication, telemetry, and external tool dependencies; a workflow is offline only if every required dependency has an offline substitute.
- A hosted agent service is inherently dependent on the cloud control/data plane for hosted execution, even if some retrieval content is cached locally.
- Session IDs are an orchestration/state concept; they do not make a hosted agent offline.

### Open

The exact component mapping depends on the original diagram and product versions and should not be generalized without the source diagram.

## Cross-cutting lessons from the period

1. **Consistency is scoped.** Strong consistency in one store does not provide exactly-once semantics across queues and external providers.
2. **Control-plane quota and data-plane routing are different.** A gateway can distribute load but cannot redefine a backend service’s quota domain.
3. **Separate hot-path correctness from asynchronous enrichment.** Redirects and notification admission should not synchronously depend on analytics.
4. **Design failure modes explicitly.** Fail-open/fail-closed, leases, retry boundaries, deduplication and reconciliation are first-class architecture decisions.
5. **Quantify before optimizing.** Average/peak RPS, backlog, working set, quota windows, and latency budgets should drive component selection.
6. **Persist explicit business state.** Conversation/session context is useful but should not be the sole store for correctness-critical application state.
7. **Keep assumptions visible.** Product limits, Azure quota scope, and service behavior that can change must remain tagged as validation items.
